# CaddieInsight Mobile Implementation Index

The approved native-app design is implemented through four independently
testable plans. Execute them in this order unless a plan explicitly marks work
as parallel-safe:

1. [Mobile Backend Foundation](2026-08-06-caddieinsight-mobile-backend-foundation.md)
   adds stable contracts, challenge-bound native sign-in, resumable uploads,
   native resource APIs, push delivery, and privacy-safe telemetry while
   preserving every current web/PWA route.
2. [Expo Coaching Client](2026-08-06-caddieinsight-expo-coaching-client.md)
   builds the coach-first iOS/Android experience on the foundation APIs. Its
   read-only shell can begin after Backend Tasks 1-4; capture/upload depends on
   Backend Task 5, privacy/export/reset/delete depends on Backend Task 6, and
   push/reminders/security notices depend on Backend Task 7.
3. [Unified Native Entitlements](2026-08-06-caddieinsight-unified-native-entitlements.md)
   adds the source-aware entitlement ledger, Apple/Google verification, server
   notifications, restore, and native purchase UI. Backend contract work may
   begin beside the client, but purchase UI waits for the coaching shell.
4. [Beta and Store Release](2026-08-06-caddieinsight-beta-store-release.md)
   adds mobile CI, EAS profiles, real-device evidence, controlled beta gates,
   and approval-gated store operations. It starts after the first vertical
   slice and cannot declare public availability until Plans 1-3 pass.

## Shared contract registry

All four plans use these exact boundaries:

- Backend source of truth: `swinglab.web.app.create_app`, `UserStore`, and
  `JobManager` in the existing single-replica SQLite/Railway topology.
- Recovery-control exception: one independently protected, least-privilege,
  append-only non-PII recovery-fence record chain plus cutover-baseline pointer
  must be read back at startup/restore after activation. It prevents old backups
  from resurrecting revoked/erased state and is not object storage for the SQLite
  database, jobs, reports, media, or canonical artifacts. External provisioning
  and initial baseline publication remain separately approval-gated.
- Client source of truth: one strict TypeScript Expo SDK 57 project under
  `mobile/`, created with Node 22.13 or newer in the Node 22 line.
- API contract: `docs/api/openapi-v1.json`, generated by
  `scripts/export_openapi.py`; client types are generated into
  `mobile/src/api/schema.generated.ts`. Generated files are never hand-edited.
- Ordinary-customer authentication: `Authorization: Bearer
  ciat_<selector>.<secret>` after a PKCE-style email-link exchange. The narrow
  store-review exception uses its dedicated provider credential plus PKCE exchange
  to issue the same short-lived bearer format with review scope; it never enters
  email/passwordless auth. Raw bearer credentials live only in SecureStore.
- Retry contract: every retryable mutation carries an `Idempotency-Key` or uses
  an explicitly tested protocol-specific conditional/idempotent contract such as
  upload offset plus checksum; server/database state, not the UI, owns replay
  safety.
- Cache invalidation: a changed `history_epoch` clears all private swing,
  practice, progress, pending-write, and staged-upload metadata before refetch.
- Environment boundary: before reading credentials/private state or making a
  request, the client verifies an immutable build environment plus canonical API-
  origin marker. Any missing/change marker durably purges every prior environment's
  secret, operation envelope, cache, and staged media before fresh sign-in; this
  is mandatory because preview and production share the store app identity.
- Push boundary: Expo tokens can also survive that upgrade. Version 1's staging
  push lane is therefore closed, TTL-drained, recovery-fenced/purged, and stripped
  of its sender credential before production registration; the same-token physical
  upgrade must prove staging cannot target the production install. Staging remains
  polling-only while public production exists.
- Commerce split: Apple/Google billing is for digital Pro; Shopify browser
  checkout is for physical gear only.
- Release state: report implementation commit, GitHub `main`, Railway health,
  PWA state, Apple approval/publication, and Google approval/publication as six
  separate facts.

## Global stop conditions

Stop and request review before any change that would:

- replace SQLite/local artifacts or increase Railway above one replica;
- broaden the approved recovery-control exception into canonical app/media
  storage or bypass its head/full-chain readback after fenced state exists;
- remove or change an existing route or response key;
- make a public deployment, submit a store build, publish a listing, enroll a
  paid account, or mutate Shopify without separate approval;
- put an email, raw video, report text, swing metric, bearer token, purchase
  receipt, or advertising identifier into telemetry or a push payload; or
- advertise a capability whose backend flag and verification path are not live.
